# The six PDFs: what each one must contain

All six are HTML files in the build folder, styled by `templates/style.css` and printed to PDF by `scripts/build.sh`.
File names: `N_<PREFIX>_<Name>.pdf`, where PREFIX is the course code (e.g. `CISC221`).

| # | File | Source | Purpose |
|---|------|--------|---------|
| 1 | `1_<P>_Mock_Test.pdf` | `mock.html` in test mode | Sit it timed. Blank answers and work boxes. |
| 2 | `2_<P>_Mock_Test_ANSWERS.pdf` | the same `mock.html` in key mode | Answers in red, each with a "Why:" explanation |
| 3 | `3_<P>_Unit_Problem_Workbook.pdf` | `units.json` + `units/uN.html` + `wb_intro/outro.html` | **The centrepiece.** Problems per unit with a method, a show-your-work model and worked solutions |
| 4 | `4_<P>_Complete_Master_Reference.pdf` | `master.html` | Everything: for reviewing, or for handing to another AI as complete context |
| 5 | `5_<P>_Concepts_Notes.pdf` | `notes.html` | Teaching notes: concepts and worked examples per topic |
| 6 | `6_<P>_QA_Drill.pdf` | `drill.html` | Question → full answer → next question, ordered by likelihood (biggest, most likely first) |

The user's priority: **tests are problem-solving, so problems come first.** The workbook and the mock carry most of the value. Notes support them.

---

## 1 + 2. Mock test and answer key (one source, two PDFs)

- `<body class="__MODE__">`: build.sh writes `test` and `key` versions. Never maintain two copies.
- Deliberately **longer than the real test**, so it hits every question type the instructor uses. Say this in the instructions box.
- Organise it in Parts (A, B, C, …) by question type, in roughly lecture order. Put marks per question in `.marks`.
- Every answer goes in `.a` (hidden in the test) and is followed by `.exp` (a "Why:" shown only in the key). Table answers go in `td.blank > span.a`. Key-only reasoning columns use `.keyonly`.
- Long-answer questions get a `.work` box (s/m/l/xl). It is hidden in the key.
- Questions must be **original**: the same *types* as the instructor's practice problems, with new numbers and code. Never copy the practice problems themselves (the student has those already, and the test won't reuse them verbatim).
- End with a key-only **scoring guide**: marks per part, and which workbook unit or official problems to redo for each weak part.

## 3. Unit problem workbook (the centrepiece)

**Assume zero background.** The workbook begins with **Unit 0 "Start here"**: the prerequisites the course takes for granted, taught with cards and practice like any other unit (`assemble.py` requires it). Every unit begins with a **Words and symbols** glossary (`units.json` → `"words": [[term, plain meaning], …]`, required). Every card includes **"What you're looking at"** (`div.read`, required), which decodes the example question for a first-timer.

**The user's learning order, per problem type:** see the problem exactly as it is asked → see the answer, written exactly as it should be written → read a full explanation of the concept → a checklist. Then practise. Every practice problem must be solvable using only the cards before it. A problem whose type has no card is a **bug**. (In the first CISC 221 build, a toolchain question sat under an unrelated method box, and the "methods" were terse rule lists that showed facts without explaining them. Both are now forbidden.)

Per unit, generated by `assemble.py`:
1. **Unit header** → **the list of problem types** (built from the card titles) → **words and symbols** glossary → **key facts** (`units.json` → `"facts"`).
2. **One card per problem type** (`<!--METHOD-->`), `<div class="ptype" data-m="M1"><h3>Title</h3>` with:
   - `div.ask`: **How it's asked.** A new example question in the instructor's exact format.
   - `div.read`: **What you're looking at.** Every part and symbol of the question explained, and what is being asked.
   - `div.write`: **The answer, written exactly like this.** The full model answer: setup → reasoned steps → final answer → check.
   - `div.explain`: **How it works.** Real teaching: what the concept is, why it works (the mechanism), the rules with reasons, a diagram if useful, the traps, and a link to the lecture or official example.
   - `div.steps`: **Every time, do this.** A 2–4 step checklist.
   Include cards for the "write the code" direction, "why" questions, edge cases and tricks, not just the main reading skill.
3. The deck box (official problems for this unit).
4. **Practice set** (`<!--PRACTICE-->`, new page): 8–12 problems, each `<div class="q" data-uses="M1 M3">`. A "Uses M…" chip is shown on each problem.
5. **Solutions** (`<!--SOLUTIONS-->`, new page): the same numbering and chips, written in the cards' answer format.

Optional: `"learn": [N, …]` in units.json inserts notes.html sections as background reading before the cards.

Around the units: `wb_intro.html` (how to use it, explaining the card order; the show-your-work habits; costly errors; a units table) and `wb_outro.html` (a mixed review set; each problem is tagged with the units' cards it uses, e.g. "Uses U2 M3 · U3 M5", then point to the mock).

**`assemble.py` FAILS the build** if the first unit isn't Unit "0", if a unit has no words glossary, if a card lacks ask/read/write/explain, if a problem lacks data-uses or uses an undefined card, if a card is never practised, if the practice and solution numbering differ, or if a learn section is missing from notes.html.

## 4. Master reference (AI-handoff document)

It must be self-contained enough that another AI given only this PDF could tutor the course. Sections:
- **A. Scope and assessment context**: course, instructor, textbook, which assessment, the list of official practice problems, recurring framing from the lectures.
- **B. Lecture-by-lecture notes**: every lecture, including the slide code and examples, definitions and lists the instructor used (be thorough; this is the "everything" document).
- **C. How the instructor solves problems**: from any revision video or worked solutions: the order covered, the annotation and drawing method, any extra examples done live.
- **D. Every official practice problem, fully solved**: the statement summarised in your own words with the essential data (do not transcribe textbook text), the answer, the steps, and traps. Flag any place where the official solution slide is incomplete or wrong.
- **E. Problem-type taxonomy**: type → how to recognise it → solving algorithm.
- **F. Traps and common mistakes.**
- **G. Reference tables** (formulas, instructions, conventions…).
- **H. Glossary.**
- **I. Quick self-test bank** (question → answer table).
- **J. Exam-day checklist.**
- At the top, add a "For an AI reading this" note: conventions, notation, and the expected answer style.

## 5. Concepts notes

Topic by topic: the idea → the rules to memorise → a worked example in the instructor's style → a small "Try it" with the answers right below. End with a one-page cheat sheet and a table "how to attack each question type".

**Write the notes before the workbook.** The workbook reuses these sections as its "Learn it" pages. Start every section with a marker comment on its own line, `<!-- 1 -->`, `<!-- 2 -->`, … just before its `<h2>`. Make sure each section teaches everything the matching unit's problems need, including the facts behind "why" questions and the "write the code" direction.

## Mock test coverage
Every mock question must map to a workbook unit's method. The key-only scoring guide maps each Part → the workbook unit to redo.

## 6. Q&A drill (question → answer, ordered by likelihood)

The user asked for this explicitly: "a pdf of question, answer, question answer, that I can work through to learn the concepts … start with bigger problems that are more likely to appear."
- **20–30 new questions**: the instructor's question types with new numbers and code (never copies of the practice problems).
- **Order by likelihood and weight:**
  - Part A: the big "write/fill in the code" problems the instructor stresses most;
  - Part B: the table and medium questions;
  - Part C: the short questions.

  Say in the intro note what the ranking is based on (e.g. which official problems the revision video spent the most time on). Tag each question with its type and source style ("Practice Problem 3.18 style").
- **Each question is followed immediately by `div.ans`**, containing in order:
  - `p.look` "What you're looking at", which explains the question's parts and symbols for a beginner;
  - the `<pre>` worked answer, written exactly as on the test, step by step, with a numeric check;
  - `p.why` "Why", the idea behind it in 1–3 sentences.
- The question box (`div.qq`) never splits across pages; long answers may flow across pages. Each Part A question after the first starts a new page (`class="qa big"`).
- `check_drill.py` fails the build if the drill is missing, has fewer than 15 questions, lacks the Part A/B/C heads, or any answer is missing or out of order.
- Verify every computable answer with a throwaway Python check, as for the workbook.
