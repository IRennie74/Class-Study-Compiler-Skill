M1Struct layout table

How it's asked
Give the offset of each field, the alignment K and sizeof for struct S { char c; int i; short s; double d; char e; };
What you're looking at

A C struct: several named fields stored together in one block of memory. You list where each field starts (its offset, in bytes from the struct's start) and the struct's total size, sizeof.

The answer, written exactly like this
Field  Size  Align  Offset  Padding before
c      1     1      0       —
i      4     4      4       3 (1..3)
s      2     2      8       —
d      8     8      16      6 (10..15)
e      1     1      24      —
end = 25 → K = max(1,4,2,8,1) = 8 → round 25 up to a multiple of 8 → sizeof = 32
How it works

A struct is one block of memory with its fields in the order declared. The compiler never reorders them. Each field is reached at a fixed offset from the struct's start, decided at compile time. Machine code only ever sees "8(%rdi)", never field names.

Alignment: a primitive of K bytes must start at an address that is a multiple of K (short → even, int → multiple of 4, long/double/pointer → multiple of 8). Memory is fetched in aligned 4- or 8-byte chunks, so a value that crosses a chunk boundary would need two fetches (and is worse across virtual-memory pages). To keep every field aligned, the compiler inserts padding (unused bytes) before a field when needed.

End padding: the whole struct has alignment K = its largest field's alignment, and sizeof is rounded up to a multiple of K. That way, in an array of these structs, every element (and every field in it) is still aligned. In the example, the struct ends at 25, and because of d it needs K = 8, so it takes 32 bytes.

Every time, do this
  1. Table: field, size, alignment (array → element size), offset, padding.
  2. Each offset = the next multiple of the field's alignment at or after the current end.
  3. K = the largest alignment; sizeof = the end rounded up to a multiple of K.

M2Minimise struct size

How it's asked
Reorder the fields of the struct S from M1 to make it as small as possible, and give the new size.
What you're looking at

Using the struct from M1, choose a different order for its fields so that the struct takes less memory.

The answer, written exactly like this
Largest alignment first: double d; int i; short s; char c; char e;
d@0 (8) · i@8 (4) · s@12 (2) · c@14 · e@15 → end 16
(already a multiple of 8) → sizeof = 16
(was 32: saved 16 bytes of padding)
How it works

Padding appears when a small field is followed by a field that needs a bigger alignment. If you sort the fields from largest to smallest alignment, every field starts at a position that is already suitably aligned, so the internal padding disappears and only the end padding (to a multiple of K) can remain. The lecture's S4 (char, int, char = 12 bytes) vs. S5 (int, char, char = 8 bytes) shows the same idea.

Every time, do this
  1. Sort the fields by alignment, largest first.
  2. Redo the layout table (M1).
  3. State the new size and the bytes saved.

M3Arrays of structs

How it's asked
struct S3 { short i; float v; short j; } a[10]; starts at address a. Give sizeof(struct S3) and the address of a[idx].j.
What you're looking at

a[10] is an array of 10 structs, each with the fields i, v, j. You give the struct's size and the address of field j in element idx.

The answer, written exactly like this
i@0 (2) · pad 2 · v@4 (4) · j@8 (2) · end 10 → K = 4 → sizeof = 12
&a[idx].j = a + 12·idx + 8
How it works

An array of structs is like any array (Unit 6): element idx starts at base + idx · sizeof(struct), and sizeof already includes the end padding. A field inside it adds that field's offset: &a[idx].f = a + idx·sizeof + offset(f).

The lecture's get_j does exactly this: leaq (%rdi,%rdi,2),%rax (3·idx), then movzwl a+8(,%rax,4),%eax = M[a + 8 + 4·3·idx] = M[a + 12·idx + 8].

Every time, do this
  1. Lay out the struct (M1) to get sizeof and the field offset.
  2. Address = base + idx·sizeof + offset.

M4Writing struct access in assembly

How it's asked
struct acct { int id; long bal; struct acct *next; }; Write the assembly for long nb(struct acct *p) { return p->next->bal + p->id; }.
What you're looking at

A struct whose last field, next, is a pointer to another struct of the same kind (like a linked list). p->next->bal means: follow p to its struct, take its next pointer, follow that, and read bal. You write the assembly.

The answer, written exactly like this
Layout: id@0 (4) · pad 4 · bal@8 (8) · next@16 (8) · sizeof 24
nb:  movq   16(%rdi), %rax     # rax = p->next
     movq   8(%rax), %rax      # rax = p->next->bal
     movslq (%rdi), %rdx       # rdx = (long) p->id   (int → long: sign-extend)
     addq   %rdx, %rax
     ret
How it works

With the layout known (M1), each field access is a memory operand offset(%reg):

  • p->f → off_f(%rdi), with the mov size matching f's type.
  • Following a pointer field (p->next->bal) takes two steps: load the pointer into a register, then access the field through that register.
  • When fields of different sizes are combined, extend them first: int → long uses movslq, and short → int uses movswl (or movzwl if unsigned).

The lecture's set_val loop is the model: movslq 16(%rdi),%rax (i), movl %esi,(%rdi,%rax,4) (a[i] = val), movq 24(%rdi),%rdi (r = r->next).

Every time, do this
  1. Lay out the struct and note each offset.
  2. One mov per field read; load pointer fields first.
  3. Extend narrower fields before combining them; comment every line.

M5Assembly → struct

How it's asked
Recover the struct and the C statement (p is in %rdi; the fields are int, long or pointers): 
movq   (%rdi), %rax
movl   12(%rdi), %edx
movl   %edx, (%rax)
ret
What you're looking at

Only the assembly is given. Each k(%rdi) reads a field at offset k in the struct p points to. You work out what fields the struct has and what the C did.

The answer, written exactly like this
movq (%rdi),%rax     8-byte field at offset 0, used as an address → a pointer: int *ptr
movl 12(%rdi),%edx   4-byte field at offset 12 → int (offset 8 is another 4-byte field)
movl %edx,(%rax)     store that int through ptr
struct s { int *ptr; int a; int b; };      // ptr@0, a@8, b@12
void f(struct s *p) { *p->ptr = p->b; }
How it works

Run M4 backwards. Every k(%rdi) is a field at offset k. The instruction's size gives the field's size (movq 8, movl 4, movw/movzwl 2, movb 1), and a signed extend (movslq, movswl) shows that the field is signed. A value that is loaded and then used inside parentheses is a pointer. Gaps between offsets are other fields (or padding), which you can fill in using the alignment rules.

Every time, do this
  1. List each offset with its access size.
  2. Values later used as addresses are pointers.
  3. Build the struct in offset order, then the C statement.

M6Unions

How it's asked
Give sizeof for union U { char c; int i[2]; double v; }; and for a struct with the same fields. Explain the difference.
What you're looking at

A C union looks like a struct, but all its fields share the same memory. You compare its size with a struct that has the same fields.

The answer, written exactly like this
union:  all fields start at offset 0; largest member = 8 (i[2] and v) → sizeof = 8
struct: c@0 · i@4 (pad 3) · v@16 (pad 4 after i) → end 24 → K = 8 → sizeof = 24
A union's fields share the same bytes (only one is meaningful at a time);
a struct gives each field its own space.
How it works

A union puts every field at offset 0, on top of each other. Its size is the largest member, rounded up to the union's alignment. Use it when you need only one of the fields at a time, to save space.

Because the fields overlap, writing one field and reading another reinterprets the same bits. The lecture's bit_float_t (float f; unsigned u) shows this: bit2float(u) gives the float whose bits are u, which is not the same as the cast (float)u, which converts the value.

Every time, do this
  1. Union: size = the largest member (rounded to its alignment); all offsets 0.
  2. Struct: use the layout table (M1).
  3. Explain sharing vs. separate storage.

M7Byte order

How it's asked
The int 0x11223344 is stored at address 0x200 on x86-64. List the bytes at 0x200–0x203. What would they be on a big-endian machine?
What you're looking at

A 4-byte int value and the address where it's stored. You list which byte sits at each of the 4 addresses, on two kinds of machine.

The answer, written exactly like this
Little endian (x86): 0x200: 44   0x201: 33   0x202: 22   0x203: 11
Big endian:          0x200: 11   0x201: 22   0x202: 33   0x203: 44
How it works

A multi-byte value occupies several consecutive addresses, and machines disagree about which end goes first. Little endian stores the least significant byte at the lowest address: Intel x86, and ARM on Android and iOS. Big endian stores the most significant byte first (SPARC). Some chips (ARM) are bi-endian. This matters when bytes move between machines (files, networks), or when you read a value one byte at a time.

To list the bytes, split the hex value into pairs from the right: 0x11223344 → 44, 33, 22, 11. Those go at the increasing addresses on a little-endian machine.

Every time, do this
  1. Split the value into byte pairs, padding to the full size.
  2. Little endian: rightmost pair at the lowest address. Big endian: leftmost first.

M8Floating-point code

How it's asked
(a) Where do the arguments of double mix(long n, double x, float y) arrive? (b) Write the assembly for double scale(double *p, double k) { double t = *p * k; *p = t; return t; }.
What you're looking at

C functions using double/float (numbers with decimal points). You say which registers hold the inputs, and write the assembly using the special floating-point registers %xmm0, %xmm1, ….

The answer, written exactly like this
(a) n → %rdi (integer #1)   x → %xmm0 (FP #1)   y → %xmm1 (FP #2)   return → %xmm0
(b) scale:                   # p in %rdi, k in %xmm0
      movsd (%rdi), %xmm1    # xmm1 = *p
      mulsd %xmm0, %xmm1     # xmm1 = *p · k  (= t)
      movsd %xmm1, (%rdi)    # *p = t
      movapd %xmm1, %xmm0    # return t in %xmm0
      ret
How it works

Floating-point values don't use the integer registers. x86-64 uses the SSE/AVX XMM registers %xmm0–%xmm15, 16 bytes each. One can hold a single float or double (scalar), or several packed together for SIMD (4 floats or 2 doubles at once).

  • The instruction suffix says what is inside: ss = scalar single (float), sd = scalar double, ps/pd = packed. So addss adds one float, addsd one double, and addps four floats in parallel.
  • Calling convention: FP args go in %xmm0, %xmm1 … (counted separately from %rdi …), the result goes in %xmm0, and all XMM registers are caller-saved. Pointers to doubles are still integers, so they come in %rdi.
  • Memory ↔ XMM moves use movss/movsd; whole-register copies use movaps/movapd; comparisons use ucomiss/ucomisd; xorpd %xmm0,%xmm0 makes 0.0.

The lecture's dincr is the model.

Every time, do this
  1. Assign integer and pointer args to %rdi … and FP args to %xmm0 … separately.
  2. Use ss for float and sd for double.
  3. Leave the result in %xmm0.
