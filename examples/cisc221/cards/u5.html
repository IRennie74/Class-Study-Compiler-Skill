M1push / pop

How it's asked
%rsp = 0x500, %rax = 7, %rbx = 9. Trace pushq %rax ; pushq %rbx ; popq %rcx. Give %rsp, %rcx and the stack memory after each step.
The answer, written exactly like this
Instruction   %rsp    Memory change          %rcx
(start)       0x500   —                      ?
pushq %rax    0x4F8   M[0x4F8] = 7           ?
pushq %rbx    0x4F0   M[0x4F0] = 9           ?
popq %rcx     0x4F8   (M[0x4F0] still holds 9) 9
How it works

The stack is a region of memory used last-in, first-out. On x86-64 it grows toward lower addresses, and %rsp always holds the address of the current top element (the lowest address in use).

  higher addresses   ┌─────┐
                     │  7  │ 0x4F8
            %rsp ──▶ │  9  │ 0x4F0   ← top after the two pushes
  lower addresses    └─────┘   (pushes go DOWN)
  • pushq S: first %rsp −= 8, then store S at M[%rsp].
  • popq D: first D = M[%rsp], then %rsp += 8. D must be a register. The memory is not erased; it just becomes "free".

Every push/pop moves %rsp by exactly 8 (one quad word).

Every time, do this
  1. Make columns: %rsp, memory change, registers.
  2. push: subtract 8, then write. pop: read, then add 8.

M2call / ret traces

How it's asked
(Lecture multstore/mult2 style) 400544: callq 400550 <mult2> is followed by 400549: mov %rax,(%rbx). Before the call, %rsp = 0x120 and %rip = 0x400544. Give %rsp, %rip and the top of the stack right after the call, and right after mult2's retq.
The answer, written exactly like this
Moment               %rsp     %rip       M[%rsp]     Why
before call          0x120    0x400544   —
after callq          0x118    0x400550   0x400549    push return addr (next instr), jump
after mult2's retq   0x120    0x400549   —           pop return addr into %rip
How it works

Calling a function means jumping to its code and remembering where to come back to. The stack stores that "come back here" address:

  • call Label: push the return address, the address of the instruction right after the call (the call's address + its length; from disassembly, simply the next line's address). Then set %rip = Label.
  • ret: pop the top of the stack into %rip, which jumps back to the return address.

Because each call pushes and each ret pops, calls nest naturally: if P calls Q and Q calls R, R returns to Q before Q returns to P (last in, first out). That is why the stack is the right data structure for procedures.

Every time, do this
  1. Make a table: PC, instruction, registers, %rsp, M[%rsp].
  2. call: %rsp −= 8, M[%rsp] = next address, %rip = target.
  3. ret: %rip = M[%rsp], %rsp += 8. Say whether your values are "before" or "after" each instruction.

M3Where arguments are

How it's asked
For long f(int a, long *b, char c, short d, long e, int f, long g, int h, double x), where is each argument when f starts executing?
The answer, written exactly like this
#   arg        type     location
1   a          int      %edi
2   b          long *   %rsi
3   c          char     %dl
4   d          short    %cx
5   e          long     %r8
6   f          int      %r9d
7   g          long     8(%rsp)     ((%rsp) = return address)
8   h          int      16(%rsp)
FP  x          double   %xmm0       (FP args are counted separately)
return value: %rax
How it works

Caller and callee must agree where data goes. The Linux x86-64 calling convention says:

  • The first six integer or pointer arguments go in %rdi, %rsi, %rdx, %rcx, %r8, %r9, in that order. Use the part of the register that matches the type's size (int → %edi, char → %dl …).
  • Arguments 7 and later go on the stack. The caller puts them there before call, so when the callee starts, the return address is at (%rsp), arg 7 at 8(%rsp), arg 8 at 16(%rsp) …
  • Floating-point arguments use %xmm0, %xmm1, … and are counted separately from the integer ones.
  • The return value goes in %rax (or %xmm0 for float/double).

Mnemonic for the order: Diane's Silk Dress Costs 8 9 (rdi, rsi, rdx, rcx, r8, r9).

Every time, do this
  1. Number the integer/pointer arguments 1, 2, 3 … and the FP arguments separately.
  2. Integer 1–6 → registers (size-matched); 7+ → 8(%rsp), 16(%rsp) …
  3. FP → %xmm0, %xmm1 …; the return value goes in %rax / %xmm0.

M4Frames and locals

How it's asked
(Lecture call_incr style) Draw the stack frame after the setup instructions, and explain why v1 is on the stack. 
long call_incr() { long v1 = 15213; long v2 = incr(&v1, 3000); return v1+v2; }
call_incr:  subq $16,%rsp ; movq $15213,8(%rsp) ; movl $3000,%esi
            leaq 8(%rsp),%rdi ; call incr ; addq 8(%rsp),%rax ; addq $16,%rsp ; ret
The answer, written exactly like this
  higher  │ return address │  ← 16(%rsp)   (pushed by whoever called call_incr)
          │ v1 = 15213     │  ←  8(%rsp)
  %rsp ──▶│ (unused)       │  ←  0(%rsp)
v1 is on the stack because its address is taken (&v1 is passed to incr).
A register has no address, so v1 must live in memory.
How it works

Each running function gets its own region of the stack, its stack frame. From the top of the caller's part down to %rsp it holds: the return address (pushed by call), any saved registers, local variables that can't live in registers, and an "argument build" area for calls with more than six arguments.

A function makes room with subq $N,%rsp and gives it back with addq $N,%rsp just before ret. Locals are then reached at fixed offsets from %rsp, like 8(%rsp).

A local variable lives in the frame (not in a register) when: its address is taken (&v1), it is an array or struct, or there are not enough registers. Separate frames are what make recursion work: every call gets private copies of its locals.

Every time, do this
  1. Draw a column of 8-byte boxes, return address at the top.
  2. Place each k(%rsp) local, and label %rsp.
  3. Explain why each local is on the stack (address taken, array, too many).

M5Caller- vs. callee-saved

How it's asked
True or false, with a reason: (a) after a call, %rbx still holds what it held before; (b) after a call, %rdx still holds what it held before; (c) a function that uses %r12 must save and restore it.
The answer, written exactly like this
(a) True:  %rbx is callee-saved; any callee that uses it must restore it.
(b) False: %rdx is caller-saved (3rd argument register); the callee may overwrite it.
(c) True:  %r12 is callee-saved, so it is pushed on entry and popped before ret.
How it works

There is only one set of registers, shared by every function. When yoo calls who, both may want %rdx, and who could destroy a value yoo still needs. The convention splits the registers into two groups so that each side knows its job:

GroupRegistersRule
Caller-saved%rax, %rdi, %rsi, %rdx, %rcx, %r8, %r9, %r10, %r11 (+ all %xmm)any call may overwrite them; if the caller needs a value afterwards, the caller must keep it elsewhere
Callee-saved%rbx, %rbp, %r12, %r13, %r14, %r15 (+ %rsp)a function that uses them must push them first and pop them before returning, so they look untouched to its caller

The lecture's main/fun1 story: main needs x and y after calling fun1, but they were passed in %rdi/%rsi, which fun1 will reuse. So main keeps copies in callee-saved registers (%rbx, %r12).

Every time, do this
  1. Name the group the register belongs to.
  2. Callee-saved → survives calls, and must be pushed/popped by anyone who uses it.
  3. Caller-saved → may be destroyed by any call.

M6Writing a function that makes calls

How it's asked
Write the assembly for long g(long x) { long a = h(x); return a + x; }.
The answer, written exactly like this
g:                       # x in %rdi
  pushq %rbx             # save the caller's %rbx (we are about to use it)
  movq  %rdi, %rbx       # keep x in callee-saved %rbx: it is needed AFTER the call
  call  h                # x is already in %rdi as h's argument; %rax = a
  addq  %rbx, %rax       # a + x
  popq  %rbx             # restore the caller's %rbx
  ret
How it works

The question to ask about every value is: "Do I still need it after a call?"

  • If no, leave it anywhere (argument registers, %rax …).
  • If yes, it must survive the call, so put it in a callee-saved register (%rbx, %rbp, %r12–%r15) or on the stack. Because you are now using a callee-saved register, you must push it at the start and pop it before ret, so your own caller isn't disturbed.

Order: prologue (push the callee-saved registers you'll use) → move the values that must survive into them → set arguments → call → use %rax → epilogue (pop in reverse order, since the stack is LIFO) → ret. This is exactly the lecture's call_incr2 and the textbook's P/Q example.

Every time, do this
  1. List the values needed after each call, and give each a callee-saved register.
  2. Push those registers; copy the values in; set args; call.
  3. Combine the results in %rax; pop in reverse order; ret.

M7Recursion → C

How it's asked
(Practice Problem 3.35 style) Fill in the C for this function, with x in %rdi. 
long rf(long x) {
  if (______) return ______;
  long nx = ______;
  long rv = rf(nx);
  return ______;
}
rf:  movl  $0, %eax
     testq %rdi, %rdi
     jle   .L1
     pushq %rbx
     movq  %rdi, %rbx
     subq  $3, %rdi
     call  rf
     addq  %rbx, %rax
     popq  %rbx
.L1: ret
The answer, written exactly like this
(a) base case:   testq ; jle .L1 with rax = 0   → if (x <= 0) return 0;
(b) saved value: rbx = x                        → x is needed after the call
(c) argument:    rdi = x − 3                    → nx = x - 3;
(d) combine:     rax = rv + x                   → return x + rv;
long rf(long x) { if (x <= 0) return 0; long nx = x - 3;
                  long rv = rf(nx); return x + rv; }
Check: rf(7) = 7 + rf(4) = 7 + 4 + rf(1) = 7 + 4 + 1 + rf(−2) = 12
How it works

A recursive function in assembly is just a function that calls itself. The normal rules (M3–M6) make it work, with no special mechanism. Every recursive function has the same four parts, and each one leaves a fingerprint in the assembly:

  • Base case: a test near the top that jumps straight to ret. %rax at that point is the base value.
  • Saved value: whatever goes into a callee-saved register (%rbx) before the call is needed after it. That is why it is there.
  • Recursive argument: how %rdi is changed just before call.
  • Combine: what is done to %rax (the recursive result) after the call.

Each level has its own frame, so each level's saved %rbx is different (the push and pop pair keeps them separate).

Every time, do this
  1. Write the four answers (a) to (d) with the line that shows each.
  2. Assemble the C.
  3. Check by evaluating a small input.

M8Recursion tables and stack depth

How it's asked
For rf from M7: (a) give a call table for rf(7); (b) when the innermost call starts, how many bytes lower is %rsp than at the entry of rf(7)?
The answer, written exactly like this
(a) level  x in   rbx saved   returns
    1      7      7           7 + 5 = 12
    2      4      4           4 + 1 = 5
    3      1      1           1 + 0 = 1
    4      −2     (base: no push)   0
(b) each recursing level pushes %rbx (8) and a return address (8) = 16 bytes
    levels 1–3 recurse → 3 × 16 = 48 bytes lower
How it works

A recursion trace has two directions. Going down (the calls), you fill in the incoming argument and the saved register for each level until you hit the base case. Coming back up (the returns), each level combines its saved value with the result from below. Fill the "returns" column bottom to top.

For stack depth, count what each level adds to the stack before the next call: one 8-byte slot per pushq, one per subq $8, and 8 more for the return address that call pushes. The base-case level, if it doesn't push, adds nothing. The lecture's pcount_r trace with x = 0110 is the model for this.

Every time, do this
  1. Table columns: level, argument, saved register, return value.
  2. Fill downward to the base case, then fill the returns upward.
  3. Depth = (number of recursing levels) × (8 per push + 8 for the return address).
